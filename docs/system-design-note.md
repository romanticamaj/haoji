## 1. 三種部署情境（核心張力）

同一份程式碼要服務三個目標，而它們的最佳解**方向相反**：

| | 自用 / 開發 | 雲端省錢 | 企業地端 |
|---|---|---|---|
| ASR | 自架 Breeze（GPU） | serverless GPU | 自架，可氣隙 |
| LLM | 自架 Ollama gemma4 | **雲端 API**（省一半 GPU） | 自架，**禁止外連** |
| 對外連線 | Tailscale | 公開端點 | **零外連**（賣點） |
| 成本 | 已有硬體 | ~$10–20/月 | 一次性 ~$4–6k |

**關鍵**：這三種 profile **不需要不同的程式碼**。config 全 env 驅動（`ASR_BASE_URL` / `OLLAMA_BASE_URL` / `LLM_MODEL` / `WEB_PORT` / `DATA_DIR`），加上 `llm.py` 的 `get_provider()` 抽象，換設定即可切換。設計時要**維持這個性質**——任何寫死位址、寫死供應商的改動都會破壞它。

⚠️ 常見誤判：為了省錢把 LLM 換成雲端 API，對企業地端客戶是**直接出局**的反方向。兩者並存，不是二選一。

## 2. GPU 容量模型（實測，非估算）

以 RTX 5070 Ti 16GB 實測：

| 指標 | 實測值 |
|---|---|
| 轉錄速度 | **~5x 即時**（158 秒音檔 → 31 秒完成，含串接+分軌+ASR） |
| 會議記錄生成 | 6–23 秒／場（視逐字稿長度） |
| VRAM 峰值 | **~9GB**（Breeze ~5 + pyannote ~2 + gemma4 ~4） |

推導出的容量：

- **VRAM**：16GB 舒服、12GB 勉強夠。若 LLM 走 API，需求降到 ~9GB（可用更小的卡）
- **吞吐量**：一張卡在上班時間（8h）可處理 **~40 小時音檔 ≈ 50 場一小時會議**；跑滿 24h 約 120 小時音檔
- **結論**：**一張中階卡就能餵飽數百人的公司**。GPU 不是擴展瓶頸，除非量非常大

## 3. 成本模型

**用量基準**：<20 小時錄音/月 → 換算約 **4–5 GPU 小時/月**（用量極低、且分散）

| 方案 | 月成本 | 備註 |
|---|---|---|
| serverless GPU（RunPod/Modal） | **$10–20** | 純計算只要 ~$2，但**冷啟動載模型**（3GB+4GB）是主要成本；用量分散＝幾乎每次都冷啟 |
| 雲端 GPU VM 常開 | **$180–250** | 唯一「compose 原封不動搬」的選項；以此用量等於 97% 在付閒置 |
| 地端一次性 | **$4–6k** 硬體 | 對企業：**兩年打平**，且資料不出門 |

**LLM 走 API 的成本**（2026-08 查證）：

| 模型 | 供應商 | 價格 | 一場會議 |
|---|---|---|---|
| Gemma 4 E4B（同現用） | DeepInfra（目前唯一） | $0.02 / $0.10 per 1M | **~$0.0008** |
| Gemma 4 26B A4B | OpenRouter 9 家含 Vertex | $0.05 / $0.25 per 1M | ~$0.002 |

→ 100 場/月也只要 **$0.08–0.2**。**拿掉 ollama 容器幾乎免費，且 GPU 需求砍半**。
（本機跑的是 `e4b-it-qat` 量化版；API 服務的是標準版，品質只會更好。）

**企業硬體選型**：⚠️ **不要用 GeForce（4090/5070Ti）進企業機房**——NVIDIA 驅動授權限制資料中心部署，法務會擋。
建議 **NVIDIA L4**（24GB、單槽、72W、免外接電源，可直接插進現有機架伺服器，~$2.5–3k）。

## 4. 安全現況與缺口 🔴

**目前後端沒有任何認證機制**（`app.py` 全檔無 auth/token/Depends 檢查）。

**一條可實際利用的外洩鏈**：
1. `GET /api/debug/jobs` 回傳 `in_flight` 陣列，**內含 session ID**
2. session ID 是 `uuid4().hex[:12]`（48 bits）——它是**唯一**的保護
3. `GET /api/sessions/{id}` 無需授權即回傳完整逐字稿

⇒ 任何能連到該 port 的人：輪詢 debug 端點 → 收集 ID → 讀取他人會議內容。

**其他缺口**：

| 項目 | 現況 | 影響 |
|---|---|---|
| CORS | `allow_origins=["*"]` | 任何網頁可打 API |
| TLS | 純 HTTP | 企業普遍要求 |
| **伺服器端保留** | 逐字稿＋會議記錄**永久存在 SQLite**，無刪除端點、無保留期限 | 與「結果只存手機」的對外說法有落差；企業需要明確保留政策 |

> ⚠️ **Tailscale 目前是唯一的存取控制**。現在之所以安全，是因為只有 tailnet 內裝置連得到。
> 任何「拿掉 Tailscale／改公開端點」的變更，**必須先補認證**，否則等於免費送出逐字稿 + 一台可被使喚的 GPU。

**補洞順序**（企業版與公開部署的共同前置）：
1. API token 認證 + CORS 收斂
2. debug 端點加保護或預設關閉
3. DELETE session 端點 + 可設定的保留期限
4. 反向代理（Caddy）做 TLS

## 5. 網路存取模式

| 情境 | 做法 |
|---|---|
| **企業地端** | **不開 tunnel**。內部員工走內網；遠端員工走**公司既有 VPN**。第三方 tunnel 會被資安審查退件，也違背地端初衷 |
| 自用（僅自己） | LAN only 最乾淨（錄音本來就離線可用，回家再上傳）；零成本零曝險 |
| 自用（需遠端） | VPS + 自架 WireGuard + Caddy（~$5/月，資料不經第三方），或 Cloudflare Tunnel（免費但仍是第三方） |
| ❌ 不要 | 裸 port forward——在補認證與 TLS 前等於裸奔 |

## 6. 已知限制與未決問題

- **🔴 App 的後端位址是編譯期寫死的**（`react-native-config` 把 `API_BASE` 烤進 binary，iOS ATS / Android network config 綁死特定 IP）。
  ⇒ **無法用同一個 build 服務多個企業客戶**。解法：App 內加伺服器位址設定頁／每客戶專屬 build（MDM）／改用主機名 + 正式 TLS 憑證。
  **這比 GPU 更早會擋住企業銷售。**
- **>30 秒的單一講者長段落會被截斷**：Whisper 對每個 diarized segment 的處理上限 30 秒，長獨白只會轉出前 30 秒。與退役的原生版行為一致，打包時未改。修正需搭配真實音檔迴歸測試。
- **分軌器維持 pyannote 3.1**：評估過 NeMo Sortformer，對好記更差（主要版本 CC-BY-NC **禁商用**、不擅長對話型會議、又慢又吃 GPU）。詳見 deployable-unit spec §5.3。
- **商業模式與 GPU 成本錯位**：最貴的一步（ASR 轉錄）是免費送的，付費解鎖的反而是最便宜的一步（LLM 生記錄）。任何人都能零付費燒 GPU。待研究競品商模後再決定是否調整付費點。
